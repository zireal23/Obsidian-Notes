# Market Data Publisher Model (Solace-Based Ingestion)

## 1. Overview

This document describes the **publisher-side design** for a market data ingestion system using **Solace persistent messaging**.

**Scope of this document**
- ✅ Publisher responsibilities and guarantees  
- ✅ Message format and batching strategy  
- ✅ Persistence and delivery semantics  
- ✅ Versioning philosophy (publisher-only view)  

**Out of scope**
- ❌ Consumer logic  
- ❌ Parsing, persistence, or version resolution  
- ❌ Database design  

---

## 2. Core Design Philosophy

> **The publisher emits immutable market data facts and remains completely agnostic to downstream business logic.**

Key principles:
- Publisher is **stateless**
- Publisher does **not interpret** data
- Publisher does **not deduplicate or version**
- Publisher guarantees **durable delivery**
- Publisher emits data **exactly as received**

---

## 3. Publisher Responsibilities

### The Publisher MUST
- Fetch market data from the external source
- Batch data rows for transport efficiency
- Attach accurate timestamps
- Identify the market data type
- Publish messages durably to Solace
- Wait for broker ACKs before considering data ingested

### The Publisher MUST NOT
- Decide which data is latest or valid
- Detect updates or corrections
- Deduplicate messages
- Persist data to a database
- Be aware of consumer behavior or schemas

---

## 4. Message Granularity & Batching Model

- **One Solace message = one batch**
- Each batch contains:
  - Exactly **one header row**
  - **100–200 data rows** (configurable)
- Batching is a **transport optimization**, not a semantic one
- Rows remain logically independent

### Batch Flush Conditions
- Maximum row count reached
- Maximum message size reached
- Time-based flush (e.g., interval elapsed)

---

## 5. Market Data Types

The system supports **multiple market data types** (e.g. PRICE, CURVE, VOL, SETTLEMENT).

Each message includes a **type discriminator**, allowing downstream systems to select the appropriate parser.

---

## 6. Message Payload Format (Compact & Typed)

### Canonical JSON Structure

```json
{
  "marketDataType": "PRICE",
  "batchId": "b7a1c9c2-23f4-4c71-9e34-abc123",
  "publishTimestamp": "2025-12-16T09:15:32.456Z",
  "exchangeTimestamp": "2025-12-16T09:15:32.123Z",
  "header": "instrument,price,volume,bid,ask",
  "rows": [
    "NG_JAN_26,3.245,150,3.240,3.250",
    "NG_FEB_26,3.310,200,3.300,3.320"
  ]
}
```

## 7. Header Row Semantics

- Exactly **one header row per message**
    
- Comma-separated column names
    
- Defines column order for all rows in the batch
    
- Acts as the **schema contract** for that message
    

Example:

`instrument,price,volume,bid,ask`

---

## 8. Data Row Semantics

- Each row is a **comma-separated string**
    
- Column order must exactly match the header
    
- Publisher validates only structural correctness
    
- No business validation is performed
    

---

## 9. Message Properties (Solace Headers)

In addition to the payload, the publisher sets Solace message properties:
marketDataType = PRICE
schemaVersion  = 1

Purpose:

- Enables routing and filtering
    
- Avoids payload inspection for type detection
    
- Supports future evolution
    

---

## 10. Timestamp Semantics

The publisher includes **truthful timestamps only**.

### Required Timestamps

- **Exchange / Event Timestamp**
    
    - When the data was generated by the source
        
- **Publish Timestamp**
    
    - When the message was published to Solace
        

The publisher does not derive or adjust timestamps.

---

## 11. Delivery & Persistence Semantics

### Messaging Mode

- **Persistent messages**
    
- Guaranteed delivery
    

## 12. Publisher Flow (Step-by-Step)

```json
1. Fetch market data from source
2. Accumulate rows into a batch
3. Generate batchId
4. Attach timestamps and marketDataType
5. Serialize payload
6. Publish persistent message to Solace topic
7. Wait for broker ACK
8. On ACK → discard local batch
9. On failure → retry publish

```

---

## 13. Failure Handling (Publisher Scope)

### Solace Unavailable

- Retry publish with backoff
    
- Do not drop messages
    
- Do not advance source cursor
    

### Duplicate Publish

- Allowed
    
- Publisher makes no attempt to deduplicate
    

### Malformed Batch

- Entire batch rejected
    
- Logged with batchId
    
- Optional quarantine handling
    

---

## 14. Versioning Philosophy (Publisher Perspective)

> **Publisher emits immutable events; versioning is a downstream concern.**

- All updates and corrections are published as new events
    
- Publisher does not compare against previous data
    
- Accurate timestamps enable downstream version resolution
    
- Publisher remains fully agnostic to persistence rules
    

---

## 15. Security & Isolation

- Dedicated Solace credentials
    
- Publish-only permissions
    
- TLS enabled
    
- No consume or browse access
    

---

## 16. Observability (Publisher Metrics)

The publisher emits metrics such as:

- Batch size (row count)
    
- Publish latency
    
- Broker ACK latency
    
- Retry and failure counts
    
- batchId for traceability

## 18. Publisher Summary

> **The publisher is a stateless, durable event emitter that batches market data into compact, typed messages and persists them to Solace without applying any business logic or versioning decisions.**
